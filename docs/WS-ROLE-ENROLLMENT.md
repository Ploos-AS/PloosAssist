# Authenticated WebSocket role enrollment

After the existing Ed25519 challenge/proof handshake, the loopback-only WebSocket endpoint accepts **one** `role_enroll` JSON message with `role` (`host` or `technician`) and the matching pairing `capability`. The server derives the connection ID from the verified socket and session ID from the authenticated handshake; neither is accepted from the role message. It verifies the independent pairing credential against the shared pairing store and returns `{"type":"role_enrolled","role":"host"}` (or `technician`). Invalid credentials, repeated enrollment, unsupported messages and signaling attempts close the socket with a policy violation. Capabilities are never echoed or logged.

This is **not** consent. The server still rejects offers, answers, candidates, screen sharing and remote input. The current development pairing API is loopback-only and its technician capability is issued through a local HTTP request; production-grade secure pairing and credential delivery are not implemented. Role revocation after enrollment and immediate transport shutdown on session revocation are also incomplete. Do not expose this prototype outside loopback.
